## Identidade e politica

Mantemos `balaio-local-admin` e acrescentamos uma identidade estatica
`balaio-profile-service`, com par aleatorio independente. Associar a identidade
a uma politica IAM pelo campo `policyNames`, com documento em `policies[].content`.
Evitar as permissoes legadas amplas `Read`, `Write` e `Admin` na identidade consumidora.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::balaio-media/profile/*"
    },
    {
      "Effect": "Deny",
      "Action": "s3:ListAllMyBuckets",
      "Resource": "*"
    }
  ]
}
```

O campo `content` da configuracao SeaweedFS recebe esse documento serializado
como string JSON. A configuracao com credenciais deve ser construida em tmpfs
como no PI-213, escapando os valores e removendo-os do ambiente do processo weed.
A configuracao estatica permite manter `-s3.iam.readOnly=true`.

Variaveis entregues ao Profile Service sao `MEDIA_S3_ENDPOINT` com
`http://seaweedfs:8333`, `MEDIA_S3_REGION=us-east-1`,
`MEDIA_S3_BUCKET=balaio-media`, `MEDIA_S3_ACCESS_KEY_ID` e
`MEDIA_S3_SECRET_ACCESS_KEY`. O servidor SeaweedFS tambem precisa receber o par
consumidor para autentica-lo. Gateway, frontend e outros consumidores nao devem
receber esse par nem as credenciais administrativas.

`prepare-local-storage.ps1`, chamado pelo setup existente, gera cada par completo
ausente ou vazio com 16 bytes aleatorios na access key e 32 bytes no segredo,
representados em hexadecimal. Preserva pares validos byte a byte, rejeita pares
parciais/invalidos e duplicatas e recusa reutilizacao da access key ou segredo
administrativo na identidade consumidora. Os valores reais ficam apenas no
`.env` ignorado; `.env.example` contem os dois novos placeholders vazios.

`storage/profile-s3-policy.json` contem somente a politica publica, sem segredos.
`start.sh` monta o JSON de identidades/politicas em `/tmp` (tmpfs, modo 0600,
usuario seaweed) e remove ambos os pares do ambiente do processo weed.
O profile storage continua opcional. A configuracao MEDIA_S3 e vazia no
primeiro start; ao habilitar o endpoint, o Profile exige o par completo.
Para compatibilidade com snapshots e fixtures do PI-213, o entrypoint ainda
aceita ambos os valores consumidores ausentes, mantendo somente o administrador;
um par consumidor parcial e sempre recusado. Os roteiros antigos de restauracao
recuperam a identidade administrativa do snapshot. A recuperacao completa do
acesso consumidor tambem exige preservar seu par no `.env` em copia protegida.
Nenhum roteiro de backup foi executado nesta entrega.

## Preparar e testar

Na pasta `platform`, usando PowerShell 7.2+ no Windows e Docker disponivel

```powershell
./scripts/setup-local.ps1
docker compose config --quiet
docker compose --profile extended config --quiet
docker compose --profile extended --profile storage up --build -d
./scripts/test-storage-provisioning.ps1
./scripts/test-profile-storage.ps1
./scripts/test-local-storage.ps1 -IncludeSpecialCharacterTest
```

Somente `seaweedfs` e `profile-service` precisam ser recriados para receber
as novas variaveis. Restart nao atualiza o ambiente de um container existente.
O Profile Service integrado interpreta essas variaveis e fornece os endpoints
de imagem, preservando os contratos atuais do PI-171.

O teste de provisionamento usa configuracao descartavel sob `secrets/`, gera
certificados proprios e remove apenas a fixture unica criada por ele.
O teste de acesso usa cliente separado na rede Docker com as credenciais do
Profile Service, confere as cinco variaveis no container real e testa tres objetos
diagnosticos unicos. O administrador prepara os dois objetos dos outros dominios
para provar recusa sobre objetos existentes. A limpeza fica limitada a esses
objetos e ao nome unico de bucket usado para testar criacao negada. Nao usar um
nome de objeto recebido do usuario para ampliar essa limpeza.

## Provas executadas

Foram utilizados dois containers descartaveis da imagem exata, com rede `none`,
sem portas publicadas e com `/data` e `/tmp` em tmpfs. Credenciais aleatorias
existiram em memoria e no container temporario. Os dois containers foram
removidos ao concluir. Nenhum backup foi criado.

As provas utilizaram S3 SigV4 via curl no proprio container. O administrador
criou o bucket e objetos conhecidos em `profile/`, `catalog/` e `community/`.
A segunda prova acrescentou a negacao explicita de `ListAllMyBuckets`.

- PUT e GET de objeto em `profile/` retornaram 200, DELETE retornou 204.
- GET, PUT e DELETE de objetos existentes em `catalog/` e `community/`
  retornaram 403. O administrador continuou lendo os objetos apos as recusas.
- Leitura fora do limite `profile/`, em `profile-other/`, retornou 403.
- Criacao e exclusao de bucket retornaram 403 para o consumidor.
- GET, PUT e DELETE da politica do bucket retornaram 403.
- ListObjectsV2 com prefixo `profile/` retornou 403.
- GET e PUT de ACL de objeto em `profile/` retornaram 403.
- ListBuckets retornou **200 com lista vazia**, mesmo com Deny explicito.
  A expectativa de recusa HTTP 403 usada no teste falhou nas provas.
- Logs da segunda fixture foram conferidos em memoria, com coleta bem-sucedida.
  Nenhum dos quatro valores aleatorios de credenciais foi identificado.

Os testes existentes `test-local-storage.ps1` passaram no principal, incluindo
upload/download com hash, autenticacao host/Docker, recusa anonima, mTLS e logs.
Compose padrao/extended validos e 13 containers principais running/healthy.

## Limitacao aceita

O codigo da versao 4.53 desvia ListBuckets da autorizacao global e decide a
visibilidade de cada bucket no handler. A resposta vazia permanece HTTP 200.
O Deny de `s3:ListAllMyBuckets` nao produz recusa HTTP. O usuario aceitou
explicitamente HTTP 200 com lista vazia para prosseguir com a politica restrita.

O teste automatizado exige que a resposta nao contenha buckets. Os tres acessos
de objeto permanecem limitados ao prefixo, com recusa das operacoes administrativas
verificadas. O consumidor nao recebe `Admin`, `Read`, `Write` ou `List` legados.

Se HTTP 403 em ListBuckets for obrigatorio, investigar uma versao corrigida ou
um ponto de acesso que imponha essa restricao, com nova prova isolada antes de
alterar a infraestrutura. Nenhuma dessas alternativas foi implementada ou
validada nesta investigacao.

## Evidencias da implementacao

- Instalacao nova isolada gerou dois pares distintos e certificados validos.
- Repeticao do preparador manteve hashes de env e certificados identicos.
- Atualizacao de fixture PI-213 preservou o par administrativo e gerou o consumidor.
- Par parcial, access key invalida, duplicata e reutilizacao administrativa foram
  recusados sem sobrescrever o arquivo de entrada.
- Setup principal acrescentou somente as duas variaveis consumidoras. Repeticao
  do setup preservou todos os arquivos. JWT, SMTP, token interno, senhas e TLS
  anteriores foram preservados.
- No storage principal, PUT/GET/DELETE do consumidor em `profile/` funcionaram
  com bytes identicos. GET/PUT/DELETE em `catalog/` e `community/` retornaram 403.
  Objetos dos outros dominios mantiveram o conteudo e foram removidos pelo teste.
- ListObjectsV2, GetBucketPolicy e CreateBucket retornaram 403 no principal;
  ListBuckets retornou 200 vazio, conforme aceite. Operacoes destrutivas sobre
  bucket/politica foram verificadas somente nas fixtures isoladas anteriores.
- O teste existente do PI-213 valida o administrador, recusa anonima, mTLS e
  caracteres especiais. A identidade administrativa continua operacional.
- As cinco variaveis foram conferidas no container do Profile Service. Gateway,
  frontend e outros servicos nao recebem o par consumidor. O processo weed foi
  inspecionado com seu usuario e nao contem os quatro valores de credenciais
  em variaveis de ambiente; Docker exec mantem a configuracao para healthchecks.
- Compose padrao e extended passaram em `config --quiet`, com 7/13 servicos.
  Os 13 containers principais terminaram running/healthy. Foram recriados
  somente SeaweedFS e Profile Service para aplicar o ambiente atualizado.
- Os arquivos candidatos ao Git foram verificados contra os quatro valores S3
  reais e marcadores PEM privados, sem ocorrencias. `git diff --check` e
  `git diff --cached --check` passaram. Essa verificacao cobre o estado local
  atual e nao constitui auditoria de todo o historico.

Os objetos temporarios nao sao fotos de usuarios. Autorizacao por proprietario,
validacao de imagens e nomes seguros pertencem ao Profile Service na Etapa 3.
Esta identidade permite operar todo `profile/*`; o backend deve separar os usuarios.
